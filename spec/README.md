# The spec is the source

This branch is an experiment: one hand-written specification,
[`std-uritemplate.spec.md`](../std-uritemplate.spec.md), from which the Python, Java and
C# implementations of std-uritemplate are generated by a language model, gated by the
project's conformance suite, pinned in a lockfile, and checked in CI without any model
call. No implementation file on this branch is edited by hand.

## Why

std-uritemplate ships the same RFC 6570 expander in ten languages. They were ported by
hand from the Java original and kept in step by hand: the same enums, the same twenty-odd
functions, the same control flow. Every cross-cutting fix is ten edits, and the ports
drift anyway. A 2026 audit found cases where four ports dropped a literal comma, one port
silently skipped unsupported value types, one never loaded a module it used, and all of
them disagreed with the RFC in the same handful of places, because the one thing nobody
ever wrote down was the algorithm itself.

The idea is old. Knuth's literate programming puts one document first and derives the
compilable code from it. What is new is the direction: there, code is the truth and prose
explains it; here, prose plus pseudo-code plus a test suite are the truth and the code is
derived, once per language. It is closer to protobuf or model-driven engineering than to
an essay, and the only reason it is worth trying now is that the "compiler" from
pseudo-code to idiomatic Python, Java or C# can be a language model.

Scala 3.10's experimental spec strings explore a related idea with the prompt inline in
the source. With ten targets the spec is the only thing that is not duplicated ten
times, so it has to live outside any one of them.

## How it works

```
std-uritemplate.spec.md ──► specc.py build --target X ──► X's source file
   A constraints                  │                          (committed, with a
   B data model                   ├─ prompt = A+B+C + X's   header and one
   C one pseudo chunk per fn      │   notes + current file   "spec: fn" marker
   D per-target notes             │   as anchor              per function)
   E conformance decisions        ├─ model call (pluggable)
                                  ├─ conformance suite through X/test.sh
                                  │   (fail → feed the failing cases back, bounded)
                                  └─ std-uritemplate.lock.json
                                       spec, chunk, notes, prompt and output hashes,
                                       backend, model, attempts, cost
```

`specc.py check` is the CI side: headers carry the current spec hash, file hashes match
the lock, every declared function has exactly one marker, no forbidden import. It never
calls a model.

"Deterministic" means three things, each checked separately:

1. **Behavioural.** Output is accepted only if the whole conformance suite passes
   through the target's own harness. The fixtures are the type checker.
2. **Structural.** The spec declares the function set; the generated file must contain
   exactly that set, in order, marked.
3. **Reproducible by pinning.** The lock records what produced each file. Regeneration
   is an explicit, reviewed action, like a dependency bump. Bitwise reproduction across
   model versions is not a goal, the same way nobody expects it across compiler versions.

Non-determinism is confined to the model call and boxed on four sides: the current file
is passed as an anchor so unchanged functions come back textually identical, the
fixtures decide behaviour, the markers decide structure, the lock makes any deviation
visible. The differential property tests in `tests/differential` are the fifth side:
every pair of targets must agree on random inputs the fixtures never covered.

## Results so far

All three targets were generated with `claude-opus-5-5` through the Claude Code CLI.

| Target | Conformance | Attempts | Cost | Notes |
|---|---|---|---|---|
| Python | 446/446 | 1 | $0.27 | first target; the hand-written file was the anchor |
| Java   | 446/446 | 1 | $0.44 | Java 8 target, UTF-16 walked as code points, Maven builds it |
| C#     | 446/446 | 1 | $1.11 | netstandard2.0 + net8.0, nullable, warnings as errors |

- Differential tests across the three (100 random cases per pair plus seeds): 109
  passed, 0 failed. The hand-written Java and Python disagreed on eight variable-name
  cases; the generated ones agree, because both follow the spec.
- A comment-only change to one pseudo-code chunk regenerated Python with only the header
  hash line changed (453 lines identical). Small spec diffs give small code diffs.
- A spec change that touches no chunk of a target (adding another target's section)
  refreshes that target's header and lock with no model call.
- The spec follows RFC 6570 where the hand-written ports did not (unreserved set, reserved
  expansion of non-ASCII, variable-name allow-list). Section E lists each decision with
  the fixture that pins it, and the divergences not yet pinned.

## Try it

Prerequisites: Python 3.8+, `jq`, the toolchains of the targets you build (Poetry, JDK +
jbang, .NET SDK 8+), and a backend. Clone with `--recurse-submodules` for the fixtures.

```
python3 spec/specc.py parse                     # what the spec declares
python3 spec/specc.py check                     # no model: is everything consistent
python3 spec/specc.py tck --target java         # conformance suite, parallel
export SPECC_BACKEND=spec/backends/claude-cli.sh SPECC_MODEL=claude-opus-5-5
python3 spec/specc.py build --target java       # regenerate if the spec changed
python3 spec/specc.py build --target java --force --model claude-sonnet-5-5
```

### Backends

The tool has no built-in model. `build` runs whatever `--backend` (or `$SPECC_BACKEND`)
names, under a three-line contract:

- the user prompt arrives on stdin;
- the system prompt is in `$SPECC_SYSTEM_PROMPT`, the `--model` value in `$SPECC_MODEL`;
- the answer goes to stdout, ideally as one fenced code block (raw code is accepted too).

`spec/backends/` has three scripts:

```
# Claude Code CLI, non-interactive, tools disabled (what produced the results above)
python3 spec/specc.py build --target python --force \
  --backend spec/backends/claude-cli.sh --model claude-opus-5-5

# any OpenAI-compatible chat completions endpoint: OpenAI, GitHub Models, Ollama, vLLM ...
# (needs OPENAI_API_KEY; OPENAI_BASE_URL for anything but api.openai.com)
python3 spec/specc.py build --target python --force \
  --backend spec/backends/openai-compatible.sh --model <model>

# no model at all: replay the committed file, to exercise the pipeline
python3 spec/specc.py build --target python --force \
  --backend 'spec/backends/replay.sh python/stduritemplate/__init__.py'
```

A coding agent CLI works the same way: wrap it in a script that honours the contract.
The lock records the backend command and model, so a run with another model is a
comparable artifact: attempts, duration, and the diff of the generated file against the
committed one. The OpenAI-compatible script was not exercised in this repository; treat
it as a template.

What to report from a run: the model, attempts and duration from the lock; whether the
anchor was respected (`git diff --stat` of the target file after a `--force` run with no
spec change should be tiny); and any conformance case the model could not fix within
`--max-attempts`, which usually means the spec is ambiguous there.

## What is hand-written, and what is not

Per target, exactly these files are hand-written, and all of them are harness or
packaging glue, not library code:

| Role | Python | Java | C# |
|---|---|---|---|
| build / setup | `init.sh`, `pyproject.toml` | `init.sh`, `pom.xml` | `init.sh`, `*.csproj`, `*.sln` |
| conformance wrapper (two files in, expansion or `false` out) | `test.sh`, `test.py` | `test.sh`, `test.java` | `test.sh`, `test/Program.cs` |

Everything else is generated. There are no hand-written unit tests: the Java JUnit test
that existed on main was removed, because a hand-written test of generated code is the
drift problem in miniature. If a native test layer turns out to be needed (the JSON
fixtures cannot express `[]int8` or `Short`, which is where the binding gaps live), it
has to be generated too, from a binding table in the target's section of the spec, and
run by `build` after the conformance suite. That is the next design step, not done.

## Fixing a bug

Never edit a generated file; `check` fails on it.

1. Add a failing case to `uritemplate-test-additional/edge-cases.json`. That is the
   language-independent bug report.
2. Run the suite. If targets disagree with each other, the spec was ambiguous: fix the
   prose or the pseudo-code in section C. If the spec was clear and one target deviated,
   add a bullet to that target's notes in section D.
3. `python3 spec/specc.py build --target <lang>` for each target whose chunks changed.
   The current file is the anchor, so the diff stays small.
4. Review the diff, then commit the spec, the fixture, the outputs and the lock together.

The escape hatch is always in the spec, never in the output.

## Adding a target

Write a `### target <lang>` section in the spec: a `target` block (`file`, `harness`,
`generated: true`, `comment`), the idiom notes (naming, error type, how to walk code
points, which stdlib calls are allowed), and the binding (which native types the harness
produces and which the library accepts). Add the harness glue (`<lang>/init.sh`,
`<lang>/test.sh` and a wrapper, see `Contributing.md`). Then `build`. Java and C# cost
one section each and one attempt each.

## Where this goes

- **Binding layer.** The abstract value model in section B, a per-target binding table in
  section D, and a generated native test per target. This is how choices like Go's
  enumerated type switch or Rust's closed `Value` enum become reviewable data instead of
  ad-hoc patches.
- **The other seven targets**, one per pull request, each starting from the audit's
  findings as its section D notes. Then a target with no hand-written ancestor (Erlang)
  to measure the real cost of a new language.
- **RFC decisions.** Each known divergence in section E becomes a fixture and a spec
  decision; the hand-written ports then have a failing test to fix.
- **Tooling.** Per-function splicing instead of whole-file anchoring, a CI job for
  `check`, a "weave" that renders spec and code side by side as documentation, a
  documented procedure for upgrading the pinned model.

## Caveats

- `tests/test.sh` keeps its scratch files in `tests/` and is not reentrant; `specc.py
  tck` runs the same cases in parallel with private temp files. `tests/test.sh <lang>`
  stays the official gate.
- The C# sources are a vendored copy of the separate `std-uritemplate-csharp` repository
  at the commit the submodule pointed to, with strong-name signing disabled.
- The GitHub workflows on this branch still list the removed languages.
